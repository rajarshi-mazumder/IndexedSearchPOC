IndexedSearch · Background

OpenSearch

What OpenSearch is, and the three ideas behind the proposed system: keyword search, vector search, and how we combine the two.

What it is

OpenSearch

  • A search engine that lets us do two things: keyword search (exact words) and vector search (meaning).
  • Open source, a community fork of Elasticsearch.
  • Ours runs on AWS (OpenSearch Serverless, Tokyo). AWS runs the servers.
  • Salesforce stays the source of truth. OpenSearch holds a searchable copy.
How it stores data
  • Each candidate is one JSON document. NoSQL: no tables, no joins.
  • All the documents live in one index (candidates), like a table.
  • On every write it also builds word lists, used by keyword search, and stores vectors, used by vector search.

1

Keyword search

Also called lexical search. Finds the query's exact words.
When a document is written

Each text field is split into lowercase words. Every word goes into a word list (an inverted index): which documents contain it, and how many times. Field lengths and totals are stored too.

Like the index at the back of a book.

At search time

The query is split the same way and each word is looked up. Every match gets points from BM25, a standard ranking formula:

  • Rarer word: more points.
  • More mentions: more points, but each extra one adds less.
  • Shorter field: more points.

Field weights are applied at search time. For example, a match in skills counts 10×, a match in the profile 1×.

Strengths
  • Exact, rare terms winKafka, SAP or J-GAAP score high because few candidates have them.
  • Easy to explainYou can say which word matched, in which field, and why it scored.
  • Fast and cheapOnly word-list lookups. No model call at search time.
Limitations
  • No synonyms“event streaming” does not find Kafka. “East Asia” does not find Japan.
  • No word forms“frameworks” does not find “framework”.
  • Long questions match looselyOnly some of the words need to match, so weak matches get in.

One word list per text field, shared by all candidates. The rarer the word (fewer documents), the more points a match gets: “localisation” (410) is worth far more than the filler word “with” (99,812).

2

Vector search

Also called semantic search. Finds the query's meaning.
Embeddings

An embedding model, Amazon Titan Text Embeddings V2, turns a piece of text into a list of 1,024 numbers: a vector. Texts with similar meaning get vectors that point in similar directions.

“Kafka engineer”→[0.021, −0.038, 0.009, … 1,024 numbers]
When a document is written

OpenSearch's ingest pipeline sends the text to the model and stores the vector next to the document, in a vector index built for fast nearest-neighbour lookup.

At search time

The query is turned into a vector with the same model. OpenSearch returns the documents whose vectors are closest (cosine similarity).

Strengths
  • Matches meaning, not words“event streaming developer” finds a Kafka engineer. “East Asia” finds Osaka, Japan.
  • Plain-language queriesThe same need, phrased differently, still lands close.
  • Works across languagesTo a degree: “東京” lands near “Tokyo”.
Limitations
  • Weak on exact rare termsA certification code or ID may not stand out.
  • No hard rules“must live in Japan” is not enforced. It always returns its nearest candidates.
  • Harder to explainA rank comes from a similarity number, not a matched word.
Meaning map

A 2-D illustration only: real vectors have 1,024 dimensions. Closer means more similar meaning. The query shares no word with “Kafka engineer”, yet it is the nearest match.

3

Hybrid search

How a search works: run both, then merge the rankings.
Run both

Keyword search and vector search run on the same index at the same time. Each returns its own ranked list.

Our system can add more vector lists, for skills, languages and region. Details on slide 2.

Merge by position

The scores are on different scales (a keyword score of 7.8, a vector score of 0.65), so adding them makes no sense. We merge by position instead, with reciprocal rank fusion (RRF):

  1. Each list gives a candidate 1 / (60 + position).
  2. Add up the points from all lists.
  3. Highest total first.
Result

Candidates that rank well in several lists win. One ranking that uses both exact words and meaning.

Why 60?

It is a tuning constant (k) from the paper that introduced RRF (Cormack, Clarke and Büttcher, 2009). 60 worked well across many test collections, and OpenSearch and Elasticsearch use it as their default too. k decides how much being near the top matters, compared with appearing in more lists.

  • Small k: whoever is #1 in any single list dominates. One quirky list can hijack the ranking.
  • Huge k: position stops mattering. RRF just counts how many lists a candidate appears in.
  • k = 60: appearing in another list is worth a lot, and a higher position still counts (#1 is worth about 1.8× #50).
